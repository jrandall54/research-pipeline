# Digest: the file you actually read

## What it does

The digest stage turns the night's kept papers into one markdown file, `<vault>/digests/YYYY-MM-DD.md`. It is the only output you normally open. Each paper gets its title (linked to arXiv), authors, the reasons it ranked where it did, its abstract, a cited summary and critique written by the local model (when one exists) and handy links. The very first line is a **health line** telling you how the run went, so a broken night is visible instead of looking like "nothing interesting happened".

It also changes the database: every paper it lists moves from `triaged` to `in_digest` and records the digest date.

## How it works

```
papers: triaged / fetched / summarized (+ in_digest for this date)
   --> attach each paper's stored summary, if any
   --> sort by score desc, then id asc
   --> render markdown
   --> write digests/YYYY-MM-DD.md
   --> mark every listed paper in_digest, digest_date = that date
```

The entry point is `write_digest(conn, vault, digest_date, run_summary)`. `run_summary` is the health line, built by the caller (the `run` command, see `running.md`) from the collect/triage counts and source errors; the digest stage prints it verbatim.

1. **Select.** Papers with status `triaged`, `fetched` or `summarized` (the summarize stage moves papers along that path; a paper whose summary failed is still `triaged` or `fetched` and is listed with its abstract only), plus papers with status `in_digest` whose `digest_date` equals this date (see "Same-day re-runs").
2. **Order.** `triage_score` highest first; equal scores break by `id` ascending, so the order is deterministic.
3. **Render** each paper (layout below). If `get_summary` returns a stored summary for the paper, the summary block (below) goes between the abstract and the links line; a paper with no summary renders exactly as before.
4. **Write** the file, creating `digests/` if needed, replacing any file of that name.
5. **Mark** the listed papers `in_digest` with `digest_date` set (`mark_in_digest` in `db.py`) and commit. The file is written first, so a crash can never leave papers marked as delivered without a file.

```markdown
id: 2411.01234 · ★ saved

**Authors:** Ann Lee, Bo Chen, Cy Diaz, Di Evans, Ed Fox et al.

```

| Part | What it is |
| --- | --- |
| Line 1 | The **health line**, exactly as passed in. |
| `# Research digest — date` | The title, with the digest date. |
| `## N. [Title](abs url)` | Rank (1 = best) and the title as a link to the paper's page. Square brackets in a title are escaped with a backslash (`\[Aligned\]`) because an unescaped `]` would end the link early and break the line; newlines inside a title are collapsed to spaces. |
| `id: ...` | The paper's id, the handle you give to `rpipe vote` and `rpipe save`. A `★ saved`, `👍` or `👎` marker follows when you have saved or voted on it (see "Feedback" below). |
| Authors | The first 5 names, then "et al." if there are more. The Jailbreaking paper had 6 authors, so only 5 are shown. |
| **Why it matched** | The score to 2 decimals and the plain-language reasons triage stored (see `triage.md`). The score is only for comparing papers within the same night. |
| Abstract | The abstract as collected, or `_No abstract available._` when the source gave none. |
| Links line | `abs` (the paper page), `PDF` (`https://arxiv.org/pdf/<id>`, only for papers with an arXiv id), HF upvotes when above zero, and one `repo` link per code repository found. |

### Feedback: ids, markers and the footer hint

Every item shows `id: <id>` right under its title. If you have saved the paper it adds `★ saved`; if your latest vote is up or down it adds `👍` or `👎` (a cleared vote shows nothing). The markers come from the `saves` and `votes` tables (`docs/guide/data-model.md`) and are read when the digest is written, so a same-day re-run shows votes you cast in between.

At the very end of the file, when there is at least one item, a single footer line reminds you of the commands, using the first item's id as the example: `rpipe vote <id> up|down · rpipe save <id>`. It appears once rather than on every item so the digest stays readable; with no items there is nothing to vote on, so no hint is written.

To go through a digest's papers one by one in the terminal, use `rpipe review` ([review.md](review.md)). You can also record feedback with `rpipe vote ID up|down|clear`, `rpipe save ID`, `rpipe unsave ID` and list it with `rpipe feedback` (see `running.md`). `ID` can also be part of a title; if several papers match you pick from a numbered list, and if none match nothing is written. **Why validate against the vault:** the database does not enforce that a vote points at a real paper, so a typo would silently store a vote for nothing; the CLI checks first. Votes are append-only (the latest one counts), so changing your mind keeps the history for later use by ranking.

### The summary block

Under a paper that has a summary, the digest shows the one-line takeaway, the four summary claims (problem, approach, results, limitations), the critique's strengths and weaknesses, and questions to ask. Every claim ends with the paper sections it cites, written `[§ 2 Method, 3 Results]`. A real rendering (paper and model output are made up; the layout is produced by the code):

```markdown
**Summary:** Gradient-searched suffixes jailbreak many aligned models at once.

- **Problem:** Aligned models can still be pushed to produce harmful text. [§ 1 Introduction]
- **Approach:** They optimise a suffix with gradient search on open models. [§ 3 Method, 4 Experiments]
- **Results:** Suffixes transfer to closed models with high success. [§ 5 Results]
- **Limitations:** ⚠ unverified Defences were not evaluated. [§ 7 Limitations]

**Strengths**

- Tests several model families. [§ 5 Results]

**Weaknesses**

- Success rates depend on one prompt set. [§ 4 Experiments]

**Questions to ask**

- Does a perplexity filter stop these suffixes?
```

- **`⚠ unverified`** in front of a claim means at least one section it cites does not exist in the paper (the code checks every cited title against the real section titles, see `summaries.md`). Treat that claim as a guess and check the paper.
- **Basis note.** A summary written from the abstract only (the paper has no arXiv HTML version) ends with the line _Summary based on the abstract only (full text unavailable)._ Its citations can only point at "Abstract". If the paper was too long for the model's context window a second note says part of it was left out.
- **No summary.** A paper whose summary failed, or that was listed while Ollama was down, shows the abstract and links only. **Same-day recovery:** start Ollama, then run `rpipe summarize` and `rpipe digest` (or `rpipe run` again) on the same day; the summarize stage also picks up papers already in *today's* digest that lack a summary (they stay `in_digest`), and the digest is rewritten with the summaries. A paper that has failed 3 times is no longer retried, on that day or later (the errors say `gave up after 3 failed tries`). Once the day has passed, the nightly run no longer touches that digest's papers, but `rpipe summarize --backlog` (or `rpipe summarize ID`) summarises them on request, and `rpipe digest --date DAY` then rewrites that day's file (see `running.md`).
- **Provenance footer.** The last line of a summary is a small italic footer, for example _qwen3:14b · prompt 2026-11-p3 · paper v2 · 2026-11-21_: the model, the prompt version, the paper version it summarised, and the date it was written. It lets you judge how much to trust a summary and spot ones made with an older model or prompt. Summaries stored before this feature have no provenance and show no footer. If a stored provenance record is partial (some fields missing), the footer shows only the fields that exist, and a record with none of them shows no footer; the digest never fails over it. See `summaries.md`.
- As always, read the paper before relying on a summary.

### The health line

One line at the top, written by the `run` command (`health_line` in `cli.py`) in exactly this shape:

```
Run 2026-11-21: collected 339 new, 11 updated · kept 15 · skipped 324 · summarized 15 · errors: none
```

`summarized N` counts papers the model summarised this run. Three more parts appear only when above zero: `abstract-only N` (summaries written from the abstract because no full text was available), `body cut N` (summaries where core paper text had to be trimmed to fit the model's context window; dropping references or appendices does not count; this is the number to watch when deciding whether long papers need splitting into chunks) and `summary failures N` (papers the model could not summarise; they keep their status and are tried again by every later `rpipe summarize` or `rpipe run`, on the same day or on later days, while they are still `triaged` or `fetched`, until the paper has failed 3 times; a paper already in an earlier day's digest is only retried by `rpipe run` on the day it was listed; `rpipe summarize --backlog` retries it later, still within the 3-failure cap). If Ollama is down or the model is missing, the stage is skipped and the cause is in the errors, for example `errors: summaries skipped, model unavailable: cannot reach Ollama at http://localhost:11434: start it with `ollama serve``. The digest is still written, with abstracts only; to fill the summaries in, start Ollama and run `rpipe summarize` then `rpipe digest` the same day (see "No summary" above).

The request list (papers you asked to have summarized; see "The request list" in `running.md`) adds up to three parts, each only when above zero: `requests done N` (requests summarized this run), `requests failed N` (requests that failed for the third time tonight and were given up on) and `requests waiting N` (requests still pending after the run: they failed with tries left, or the drain stopped or was skipped because the model hit a usage limit or timed out). For example `... · summarized 15 · requests done 1 · requests waiting 2 · errors: summarize 2611.30001: arXiv returned 503`. A request's error line appears in `errors` like any summary failure.

If the run immediately before this one never finished (the process was killed, so its `finished_at` is empty), ` · previous run did not finish` is appended after the errors. If a stage of *this* run crashed, the digest is still written and the error appears as `errors: collect: <message>` (see "Crash-safe runs" in `running.md`).

`collected N new` is the number of papers never seen before, `updated` those that changed (a new version, or new upvotes/repos), `kept` and `skipped` come from triage, `summarized` from the summarize stage. After `errors:` comes `none` or every error joined with `; ` (whitespace inside an error, including newlines, is collapsed to single spaces so the health line is always one line), for example `errors: arxiv: arXiv API returned HTTP 500; seeds: could not fetch 2302.12173: ...`. If a source failed, the digest is still written from whatever the other sources produced and the failure is stated here. A quiet digest with `errors: none` means a quiet day; one with an error means some papers may be missing. The `digest` command on its own has no run to summarise, so it writes a plain `Digest <date>: written from stored papers (no collection run)` line instead. That means running `digest` again on the same day overwrites the original health line (and any errors it showed) in that day's file; the errors are not lost, they stay in the `runs` table.

### When nothing qualified

The file is still written: health line, the heading, and the sentence "Nothing new matched your profile today." A missing file would be ambiguous (did the run crash, or was it a quiet day?), so there is always a file for every run.

### Status changes

| Before | After | Also set |
| --- | --- | --- |
| `triaged`, `fetched`, `summarized` | `in_digest` | `digest_date` = the digest's date (ISO, e.g. `2026-11-21`) |
| `in_digest` with this date | stays `in_digest` | nothing new |

Papers with other statuses (`new`, `skipped`, `failed`) are never touched. Score and reasons are left unchanged. If a newer version of a paper later arrives, the database moves it back to `triaged` (see `data-model.md`) and it can appear in a later digest.

### Same-day re-runs

Running the pipeline twice on the same date rewrites the same file. Without special handling the second run would find nothing `triaged` (the first run already moved those to `in_digest`) and would overwrite a good digest with "Nothing new". So the selection also includes papers that are `in_digest` **with this date's** `digest_date`: the rewritten file contains everything from the first run plus anything newly triaged since.

Example: the 08:00 run lists papers A and B. At 14:00 a re-run triages paper C. The 14:00 file lists A, B and C (ranked together), and all three are `in_digest` for that date. Papers delivered on an earlier date are not repeated.

## Why it's built this way

- **A markdown file in the vault**: plain text opens anywhere, works in Obsidian-style note tools, can be searched, and needs no server. Rejected: HTML or email, which add rendering and delivery problems for no gain.
- **Health line first**: you see failures at the same place you read results. Rejected: only logging errors, which nobody checks.
- **Date-matched `in_digest` on re-runs**: keeps the file complete and idempotent (same inputs, same file). Rejected: appending to the file (duplicates, messy ordering) and ignoring re-runs (loses content).
- **The caller supplies the health line**: the digest stage does not know about source failures or skipped counts; the run orchestration does. Keeps the writer simple and testable.
- **Summaries stored, rendered at write time**: the digest reads the stored summary with `get_summary`, so a same-day re-run reproduces the same text without calling the model again. A paper with no summary is still listed: a missing model must never hide the night's papers. Citations and the `⚠ unverified` flag are shown rather than hidden so you can judge each claim yourself.
- **Reasons stored, not recomputed**: the digest prints what triage decided at the time, so the explanation always matches the ranking.

## How to run / check it

Normally via the `run` command, which runs collect, triage, summarize, then digest (see `running.md`); `rpipe digest [--date YYYY-MM-DD]` rewrites just this stage. Open `<vault>/digests/<today>.md`. To inspect the effect in the database:

```
sqlite3 <vault>/vault.sqlite "select id, status, digest_date from papers where digest_date is not null"
```

Tests: `uv run pytest -q tests/test_digest.py tests/test_db.py` (offline; they use a temporary database and vault).

## Where the code is

- `src/research_pipeline/digest.py`: `write_digest` and the markdown rendering (including the summary block).
- `src/research_pipeline/db.py`: `mark_in_digest`.
- `src/research_pipeline/library.py`: `record_vote`, `current_votes`, `set_saved`, `is_saved`, `list_saved` (the digest reads votes and saves from here).
- `src/research_pipeline/digest.py`: `render_summary` is public because `rpipe review` shows the same summary text.
- `src/research_pipeline/cli.py`: the `vote`, `save`, `unsave` and `feedback` commands (`_resolve_paper` turns an id or title fragment into a paper id).
- `tests/test_digest.py`, `tests/test_db.py`, `tests/test_cli_feedback.py`.

Cited section names come from the model, so they pass through the same one-line cleaning as other model text (whitespace and newlines collapse to single spaces): a section name containing a newline or `##` cannot start a new heading or break the digest layout.
